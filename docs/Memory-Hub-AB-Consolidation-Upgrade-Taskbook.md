## 1. 目标与不在本次范围内的事项

### 1.1 目标

实现一个统一的记忆整合流程，通过配置和受控的可选请求参数，选择以下两种候选发现模式：

- **模式 A：`hybrid`，向量辅助整合。** 用现有 embedding 抽象召回语义相近候选；可与本地规则候选并集；所有候选进入同一套确定性分类、冲突检查、提案与合并决策流程。
- **模式 B：`rules`，本地规则整合。** 不请求 embedding、不查询向量相似度；使用本地规范化、指纹、结构化字段、关键词/词元和现有数据库能力发现候选。

两种模式必须共享相同的：

1. 账户与命名空间授权过滤；
2. 时间有效性与新旧事实处理；
3. 记忆类型、环境、版本和结构化字段校验；
4. 冲突识别与提案治理；
5. 自动合并安全门槛；
6. 证据溯源、审计、备份/恢复兼容性；
7. 输出格式和统计口径。

### 1.2 明确不做

- 不开发新的生成式 LLM 改写器、摘要器或记忆合并器。
- 不让 LLM 根据两条原始记忆自由生成一条“更好的综合记忆”。
- 不重建 Memory Hub 架构，不替换 PostgreSQL，不移除 MCP。
- 不为 A、B 分别复制一套数据库模型或自动合并代码。
- 不改变现有 28 个 MCP 工具的权限 Scope 要求；如需调整权限，必须证明必要性并进行安全审查。
- 不把 `mock`/伪向量当作真实语义能力，不以 mock 分数作为 A 模式发布依据。
- 不要求本次将整个系统所有认知提炼（例如对话、工作经验蒸馏）改成无 LLM；本任务限定为**记忆整合链路**。但必须审计并在文档中明确其他功能是否另行调用模型，不能把整合模式 B 宣传成全系统离线模式。

## 3. 核心设计原则

### 3.1 向量只负责“找候选”，不能负责“下结论”

Embedding 可以回答“这两条记忆值得一起检查吗”，不能单独回答“这两条记忆相同、可以合并吗”。余弦相似度高可能源自主题相近，而不是事实重复。例如：`PostgreSQL 15` 和 `PostgreSQL 16` 语义相似，但它们可能表示不同版本，不能被误合并。

A 模式的向量分数只能作为候选排序或过滤信号。任何自动合并都必须通过与 B 共用的确定性规则、字段与冲突校验，并满足现有自动合并政策。

### 3.2 两种模式共享后半段流程

目标流水线如下（实际实现可按现有架构调整，但职责必须保持）：

```text
请求 / 配置
    |
    v
解析有效整合模式与策略版本
    |
    v
按账户、命名空间、权限、有效期和状态读取候选空间
    |
    +-------------------------------+
    |                               |
    v                               v
B: RulesCandidateFinder      A: HybridCandidateFinder
本地规则候选                  本地规则候选 + embedding 候选
    |                               |
    +---------------+---------------+
                    |
                    v
          去重候选并规范化证据
                    |
                    v
        确定性关系分类与冲突检查
                    |
                    v
       自动合并安全门槛 / 待审提案
                    |
                    v
       保留证据、审计、统计与版本历史
```

### 3.3 整合与检索保持独立

- `HUB_CONSOLIDATION_MODE`（本任务建议名）只控制整合候选发现策略。
- 不改变 `HUB_EMBED_PROVIDER`、检索分数、MMR、`memory_search` 的行为与语义。
- B 模式要求的是“整合请求不调用向量”，不是“整个系统不再使用 pgvector”。不为此删除 pgvector 扩展、向量列或检索索引。
- 对外健康检查若要报告能力状态，新增独立的整合能力信息或复用现有能力结构；不要把检索 `semantic.ready` 直接等同于整合状态。

## 4. 用户可见模式定义

### 4.1 模式 B：`rules`（默认基础模式）

**目标：无 embedding 依赖，稳定、可复现、无外部模型调用。**

候选发现至少支持：

1. **精确重复：** 对原始内容执行严格一致性检查。
2. **保守规范化指纹：** 规范化不影响语义的空白、换行、Unicode 规范形式和可安全忽略的格式差异后计算稳定哈希。
3. **结构化字段匹配：** 结合 `namespace`、`key`、`kind`、`scene`、实体/关系字段、环境标签、版本标识和有效时间等现有字段。
4. **本地词法候选：** 复用当前已存在的全文索引、关键词检索、词元、n-gram 或 SQL 查询能力；如需新增索引必须先评估查询计划、写入成本和迁移风险。
5. **时间与版本候选：** 识别同实体/属性的更新候选，但不得仅凭“同一字段”直接判定为重复；必须区分更新、冲突和不同时间下的真实变化。
6. **冲突候选：** 同一业务实体的不同值、相互矛盾的事实、不同环境中的经验，应该进入冲突检查或提案，不应被去重器吞掉。

规范化必须保留会改变事实的内容，包括但不限于：否定词、数字、日期、单位、版本号、路径、代码标识符、URL、大小写敏感的令牌和环境名称。禁止使用过度清洗规则，把“不是 X”规范成“X”，或把 `v1` 与 `v2` 变成同一个指纹。

纯规则模式可以生成候选、分类、提出提案，也可以按当前安全政策合并**确定无歧义**的重复项。不得因为某条规则没有匹配到候选，就推断系统已证明两条记忆不同。

### 4.2 模式 A：`hybrid`（向量辅助模式）

**目标：提高同义改写、自然语言表述变化和跨会话表达差异的候选召回率。**

候选来源：

- B 模式已有的精确、规范化、结构化和词法候选；
- 现有 embedding provider 产生的语义候选；
- 将候选并集去重后进入相同确定性处理链。

实现要求：

1. 尽量复用项目现有 embedding provider/trait，不引入第二套无关的 HTTP 客户端或模型配置体系。
2. 仅调用 embedding 能力（例如兼容现有 provider 的 embeddings 请求）；不调用生成式补全/对话接口。
3. 向量候选分数、模型名、候选策略版本和必要的来源信息要可观测、可复现；不得把相似度直接转换成事实置信度。
4. 如果现有记忆已经保存可用且模型版本兼容的 embedding，优先按现有策略复用；不能假设全部向量可复用，必须核对维度、模型标识、归一化与度量方式。
5. 若模型或 embedding 版本不一致，不能直接比较不兼容向量；按现有重嵌入策略处理，否则返回明确的不可用/降级结果。
6. 真实模型的阈值必须通过整合专属评测标定，不能直接把检索 `min_score` 当成整合阈值，也不能使用 `mock` 结果宣称语义质量达标。
7. 候选发现阶段不得改写原始记忆，不得自动生成新摘要，不得将多条内容拼接成未被证据支持的新事实。

### 4.3 共享的关系分类

在审计现有枚举后，保证逻辑上能够区分下列情形（可映射到已有类型，不要求照抄类型名）：

- `ExactDuplicate`：原文完全相同；
- `CanonicalDuplicate`：保守规范化后相同；
- `SemanticNearDuplicate`：语义可能相同，但不能仅凭向量分数证明；
- `SupersedingVersion`：同一事实出现了有时间顺序的新版本；
- `Conflict`：内容、值、有效时间或适用环境相冲突；
- `RelatedOnly`：主题相关但应该保持两条；
- `Uncertain`：证据不足，保留分立或生成审核提案。

若当前模型不能表达这些区别，优先增补现有分类；不要为分类重复造一套与提案类型冲突的状态机。

### 4.4 合并决策矩阵

| 候选关系 | 模式 B | 模式 A | 默认处置 |
|---|---|---|---|
| 内容完全相同 | 可识别 | 可识别 | 按现有安全策略去重 |
| 保守规范化后完全相同 | 可识别 | 可识别 | 按现有安全策略去重 |
| 语义改写但结构化字段一致 | 可能漏检 | 更容易召回 | 生成可审核提案；不得仅按向量分数直接合并 |
| 同实体、同属性的新旧版本 | 由字段/时间规则识别 | 由字段/时间规则识别 | 按时间和证据封存旧版本，保留历史 |
| 同实体但值不同、时间不明确 | 识别可能有限 | 更容易召回 | 冲突提案，不自动覆盖 |
| 环境标签不同的工作经验 | 依规则处理 | 同样按规则处理 | 不能因相似度高跨环境合并 |
| 仅主题相似 | 可能少召回 | 可能召回较多 | 保持分立 |
| 没有可靠候选 | 返回无候选 | 返回无候选 | 不编造、不强行合并 |

`dry_run` 必须保持只读。提案裁决、删除、过期封存、自动合并和备份行为沿用既有机制，不得由新模式绕过。

## 5. 配置与调用方式

以下为建议配置名。实施前必须检索仓库已有配置，避免重复命名；若现有命名约定不同，使用现有风格，并在文档列出映射。

### 5.1 环境变量

```dotenv
# 默认使用纯本地规则整合，不会因为配置了检索 embedding 而自动启用向量整合
HUB_CONSOLIDATION_MODE=rules

# hybrid 依赖暂时不可用时：rules=透明降级；error=返回错误，不执行整合
HUB_CONSOLIDATION_FALLBACK=rules

# 默认禁止 MCP 单次请求覆盖服务端模式；保持管理员明确控制模型调用和数据出站
HUB_CONSOLIDATION_ALLOW_MODE_OVERRIDE=false

# 仅 hybrid 使用；若已有兼容配置，应复用现有配置；候选上限应有硬上限
HUB_CONSOLIDATION_EMBED_TOP_K=20

# 仅 hybrid 使用。必须由现有实现或真实模型专属评测给出；没有有效值时，不得静默套用检索阈值
# HUB_CONSOLIDATION_EMBED_MIN_SIMILARITY=<经评测标定的 0..1 值>
```

具体语义：

- `HUB_CONSOLIDATION_MODE` 只接受 `rules` 或 `hybrid`；其他值应在启动校验或首次使用时返回可读配置错误，不得静默猜测。
- 默认 `rules`。仅配置了 embedding provider 不应自动切换到 `hybrid`，避免意外把记忆内容发送给外部服务。
- `hybrid` 必须使用真实且就绪的 embedding provider。`mock` 或已声明语义未就绪的 provider 不得被当作有效 A 模式。
- `HUB_CONSOLIDATION_FALLBACK=rules` 时，如果 A 因网络、超时、provider 不可用或模型不兼容失败，可运行 B 的候选发现，但响应和日志必须显式说明 `requested_mode=hybrid`、`effective_mode=rules`、`fallback_applied=true` 与结构化原因。不得把降级结果标记为成功的 hybrid 评测结果。
- `HUB_CONSOLIDATION_FALLBACK=error` 时，A 不可用就返回明确可诊断的失败，不执行隐式整合；请求失败不得留下部分合并状态。
- `HUB_CONSOLIDATION_ALLOW_MODE_OVERRIDE=false` 时，MCP 调用只能使用部署默认模式；为兼容现有客户端，不要求旧请求添加新字段。
- 如果实现单次调用 `mode` 覆盖，只能在 `HUB_CONSOLIDATION_ALLOW_MODE_OVERRIDE=true` 时启用；任何请求显式选择 `hybrid` 都应被视为允许将经脱敏处理的记忆文本发送到已配置的 embedding endpoint。不可绕过 provider 健康检查与数据范围控制。
- `HUB_CONSOLIDATION_EMBED_MIN_SIMILARITY` 不得盲目复用检索 `HUB_RETRIEVAL_MIN_SCORE`。如果当前向量适配器的分数并非归一化相似度 `[0,1]`，先定义清楚度量方向和转换规则。未标定前只能在测试/显式实验环境运行 A，不得宣称生产语义整合已验收。

### 5.2 MCP 兼容性

- 现有 `memory_consolidate` 与 `memory_integrate_scan` 的旧参数必须继续有效，默认行为不得要求旧客户端更新。
- 优先将模式作为服务端配置；如果实际产品需要同一部署内逐次选择模式，可给相关工具增加可选 `mode` 参数，但必须受上述 override 开关控制。
- 不增加必填参数，不删除或重命名现有字段，不更改 JSON-RPC 封装和现有 Scope。
- 响应允许添加字段，但不能移除/重命名既有字段。建议在现有响应结构内增加类似状态信息（以实际 schema 为准）：

```json
{
  "requested_mode": "hybrid",
  "effective_mode": "rules",
  "candidate_strategy": "local_rules",
  "embedding_used": false,
  "fallback_applied": true,
  "fallback_reason": "embedding_provider_unavailable"
}
```

这只是新增状态字段的示例，不得把它当成真实响应 schema；实现时必须适配当前类型，并为枚举、错误码和字段编写序列化兼容测试。日志中禁止记录原始记忆文本、访问令牌或完整敏感 embedding 输入。

## 6. Rust 架构实施规格

### 6.1 先复用，再抽象

先确认当前候选发现和整合服务是否已有 trait 或策略对象。如果已有，扩展它；如果没有，才新增最小的候选发现抽象。不要复制业务规则到两个模式里。

逻辑上应具有下列职责（具体命名服从仓库现状）：

- `ConsolidationMode`：`Rules` / `Hybrid` 配置枚举；
- `CandidateFinder`：候选发现接口；
- `RulesCandidateFinder`：只依赖本地数据的实现；
- `HybridCandidateFinder`：组合规则候选与 embedding 候选的实现；
- `ConsolidationCandidate`：候选 ID、候选来源、可选的模型相似度、结构化比较结果；
- `CandidateRelation`：对重复、冲突、版本关系、相关和不确定情形进行分类；
- 共享的 `ConsolidationDecision`/现有同等服务：负责是否自动合并、生成提案或保持分立。

示意接口，仅表达职责，不要求按字面复制：

```rust
// 与仓库当前 async trait、错误类型和依赖约定保持一致。
// Rules 实现不得持有或调用 embedding client。
trait CandidateFinder: Send + Sync {
    async fn find_candidates(
        &self,
        context: &ConsolidationContext,
    ) -> Result<Vec<ConsolidationCandidate>, ConsolidationError>;
}
```

如果项目使用 `async_trait`、其他错误类型或同步 trait，应沿用现有做法。不要为这一小项无理由引入新框架。

### 6.2 模式 B 的依赖隔离

必须从类型、依赖或测试至少一个层面确保 Rules 实现不会误调用 embedding：

- 首选架构上让 `RulesCandidateFinder` 根本拿不到 embedding client；
- 如果现有服务难以做到完全类型隔离，使用可观测的 embedding spy/mock 证明调用次数为 0，并在代码审查中说明边界；
- Rules 模式不得读取向量相似度查询结果作为隐式后备信号；
- 数据库可以仍有 vector 列和索引，但 B 的候选选择结果不得依赖它们。

### 6.3 模式 A 的依赖隔离

- 使用现有 embedding client/trait；若缺少对应批量能力，优先扩展现有适配器。
- 限制每次候选扫描的条数、单次 batch、超时和并发数，避免大命名空间一次发出无界请求。
- 去重后统一进入共享关系分类器。
- 不创建任何生成式 LLM 请求客户端，不添加用于整合的 prompt 模板或 completion 配置。
- 对不兼容 embedding 模型、维度不匹配、空向量、非有限数（NaN/Inf）、超时、429、5xx、解析错误和中断做明确处理。

### 6.4 幂等、事务与并发

- 同一输入重复运行，不能因候选排序随机变化而不断创建重复提案或反复合并。
- 候选对与候选组必须以稳定 ID/排序去重，并对跨批结果做确定性处理。
- 沿用当前事务与并发控制模式。多个 worker 同时扫描同一命名空间时，不能重复产生互相冲突的提案、覆盖新数据或丢失版本历史。
- `dry_run` 不得写入记忆、提案、游标或外部状态；如现有系统允许记录运行审计，需明确区分只读运行日志与业务数据变更。
- 模型超时/失败发生在写操作前，必须确保没有部分合并；若现有流程有分批事务，需明确分批失败语义并逐步执行可恢复的状态提交。

## 7. 规则与决策安全要求

### 7.1 候选层与决策层分开

候选层追求适当召回；决策层追求正确性。候选多并不等于整合质量高。所有候选都必须通过统一决策层，不得让 A 自带另一套更宽松的自动合并策略。

### 7.2 自动合并规则

1. 先审计目前 `auto_merge` 的行为、阈值与回滚保证，再在原规则上进行最小增量修改。
2. 完全相同和安全规范化后完全相同的内容，可按现有策略自动去重。
3. 仅被 embedding 召回、仅有高语义相似度、或仅有高关键词重叠的内容，不得自动合并。
4. 对语义近似候选，除非能由现有结构化字段及证据证明是同一事实且不会丢失信息，否则生成提案。
5. 对相互矛盾的事实、版本号、日期、数值、单位、否定表述、环境标签、来源主体或适用条件不同的记忆，禁止自动合并。
6. 更新事实应按现有 `valid_from` / `valid_until` 或同等时间模型处理，不能物理覆盖历史；不可确认时间先后时生成冲突提案。
7. 合并后保留所有源记忆 ID、证据 ID、修订历史及来源。任何新内容都必须能够追溯到原有证据，不允许生成没有证据支持的综合结论。
8. 如果旧实现的自动合并比以上要求更宽松，不能静默扩大风险；需要增加安全门禁、兼容性说明和专项测试。

### 7.3 规则本身也要可审计

给规则判定提供稳定的原因码，例如 `exact_content_match`、`normalized_fingerprint_match`、`same_entity_conflicting_value`、`validity_period_conflict`、`environment_mismatch`、`semantic_candidate_requires_review`。使用已有枚举优先；原因码不能包含原始敏感文本。

## 8. 隐私与安全

### 8.1 A 模式的数据出站

Embedding 服务可能是本地服务，也可能是外部供应商。进入 A 模式前必须：

- 确认当前 provider 的 endpoint、模型名、数据保留策略和部署位置；文档明确记忆文本可能被发送给该 endpoint。
- 只发送候选发现所需的最小字段，不要把无关的证据原文、全部版本历史、用户令牌、账户密钥或完整 metadata 一并发送。
- 复用现有敏感信息扫描/脱敏机制；审计历史存量数据是否已脱敏，不能只假设新写入数据已处理。
- 日志不记录原文、认证头、API key 或完整请求/响应 payload。
- 如果部署无法接受数据出站，应使用本地 embedding provider 或选择 B；不能因服务已配置 provider 就自动向其发送数据。

### 8.2 B 模式的离线保证

- 单元/集成测试应通过 embedding spy、失败即报错的 client 或受控 HTTP 测试服务，证明 B 路径的 embedding 调用次数为 0。
- B 执行时不得为了“预热缓存”、计算缺失向量、模型检测或写入辅助列而偷偷调用 embedding。
- B 的日志、错误上报和指标导出也不得通过外部 AI API 处理记忆文本。
- 明确此承诺只针对整合路径。其他功能如 `memory_search`、认知提炼等是否会调用模型，需在文档中单独说明。

### 8.3 权限隔离

- 所有候选读取必须先受到当前账户和 namespace 授权限制；严禁先在全库做语义候选搜索，再在应用层过滤权限。
- 任何缓存键均需包含适当的账户/租户/命名空间隔离维度；不可让两个同名 namespace 的候选混淆。
- `memory_consolidate` / `memory_integrate_scan` 保持既有 Scope。新模式参数不得成为绕过 ACL 的旁路。
- 进行账户 A/B、同名 namespace、授权撤销、无权备份恢复等回归测试，越权必须为 0。

## 9. 数据库、迁移、备份与恢复

### 9.1 优先避免迁移

如果现有提案/审计结构已经能存候选来源和执行策略，本次不需要新增数据库字段。先用实际 schema 验证，禁止为了“设计完整”而无实际必要地扩表。

### 9.2 如确有字段缺口

如果无法在现有结构中可靠记录候选来源或模式状态，允许提交**最小、可向后兼容的增量迁移**，但必须：

- 在 migration 前写明具体需求与替代方案，证明现有字段/metadata 不足；
- 新字段可空或有安全默认值，不强迫历史记录伪造模式来源；
- 为新增字段定义版本兼容策略；旧记录可继续读取、列表、裁决和备份；
- 更新快照 schema 版本/转换器（如项目已有机制），确保旧快照可恢复到新版本；
- 测试新旧版本快照、`merge`、`replace`、checksum、失败回滚与再次恢复；
- 不做破坏性重写，不清空或重建现有记忆索引。

### 9.3 数据生命周期

- 候选扫描不删除原始记忆和证据。
- merge 仅沿用当前既定的软删除/归档/版本封存逻辑；不把源记录物理删除。
- 过期证据与备份副本的处理遵循当前保留策略，本任务不得意外修改 TTL、过期或 purge 语义。
- 若新增候选来源审计，删除和保留策略不得泄漏账户间关联信息。

## 10. 评测与测试设计

必须把“检索排序效果”和“整合质量”作为不同评测。不能用现有 retrieval Bench v2 的 Recall@K 直接宣称整合成功。

### 10.1 新增整合标注集

构建固定、可复现、带版本和数据指纹的 consolidation evaluation set。样本至少覆盖：

1. 完全相同文本；
2. 空白、标点、Unicode 变化等安全规范化重复；
3. 中文同义改写；
4. 相似主题但事实不同；
5. 数字/单位/版本号只差一位；
6. 带否定与不带否定的对照；
7. 同一事实的时间更新；
8. 日期/时间冲突；
9. 不同实体、同名实体和实体别名；
10. 环境标签冲突的 Working Experience；
11. Coding 修订与 Git revision/patch 边界；
12. 已有 open 提案的重复扫描；
13. 噪声负例与域外记忆；
14. 多账户/同名 namespace 的隔离场景；
15. 空内容、超长内容、敏感串、缺失向量及错误向量。

评测集不得带真实密钥、用户隐私或不必要的原始生产记忆。测试 fixtures 中也不能加入真实 token/secret。

### 10.2 必报指标

对 A 和 B 分别报告：

- 候选召回率（按标注的重复对/冲突对分开计算）；
- 候选精确率；
- 自动合并精确率、自动错误合并率；
- 冲突识别召回率；
- 需要审核的提案数、漏提案数；
- 每千条记忆候选数与整合耗时 p50/p95；
- embedding 调用次数、请求量/Token 或文本量（provider 可得时）、失败率与降级率；
- A 相对 B 在“语义改写重复”类别上的增益；
- 每种模式下的租户/时间/环境/版本硬约束违规数。

### 10.3 必须满足的安全门槛

- 自动合并评测集中的错误合并数为 **0**；若任何测试发现错误合并，修正策略或将该类型降级为提案，不得以总体召回提升抵消。
- 跨账户或 namespace 越权读取/合并数为 **0**。
- 时间、版本、否定、数值/单位、环境等硬边界违规数为 **0**。
- B 模式 embedding 调用次数为 **0**。
- A 模式生成式 LLM 调用次数为 **0**。
- 在语义改写的标注样本上，A 的候选召回应比 B 有明确可量化的提升；若没有提升，应检查模型、阈值和实现，不能只因接入了向量服务就认定 A 有价值。
- A 的向量故障降级行为必须与配置一致，响应真实报告 `effective_mode` 和 `fallback_applied`；降级不能被记成 A 成功样本。

发布前需记录性能门槛与样本规模。不可根据极少量样本声称普遍提升；样本不足时明确标记为暂定结果。

### 10.4 必要自动测试

**模式与调用隔离**

- 默认配置解析为 `rules`。
- 未知模式字符串被拒绝，不会静默变成 A 或 B。
- Rules 运行全流程，embedding spy 调用次数为 0。
- Hybrid 会调用 embedding provider 获取候选；不调用任何生成式 LLM 路由。
- provider 为 `mock` / 未就绪时，A 按 `fallback` 配置降级或报错。
- fallback 返回的 requested/effective mode、原因码、指标均准确。
- 单次调用模式覆盖（若实现）在 override 禁止时拒绝；启用时仍须有可用 provider 并遵守权限。

**合并质量**

- 精确/规范化重复按安全策略处理且幂等。
- 语义候选不会仅凭相似度自动合并。
- 相近但值不同、版本不同、否定不同、环境不同的样本不得自动合并。
- 旧/新事实符合现有时间有效性语义；源记录历史与证据保留。
- 重复扫描不会反复创建 open proposal。
- `dry_run` 不改变业务数据。

**失败与并发**

- embedding 超时、429、5xx、空向量、维度不符、非有限数不会造成半合并。
- 同一 namespace 的并发扫描不会重复生成冲突提案或丢失版本。
- 服务重启后整合状态与提案一致。
- 事务失败后数据库保持一致，可安全重试。

**安全与兼容性**

- 所有现有 OAuth / ACL / namespace grant 测试通过。
- 账户 A 与账户 B 的同名 namespace 不能互见候选、提案或统计。
- 撤销 grant 后不允许继续整合该 namespace。
- 旧版 MCP 请求（不包含新增 mode 字段）继续工作。
- 备份快照、`dry_run`、`merge`、`replace`、checksum 与失败回滚测试通过。
- 不把原始记忆、token 或外部模型完整 payload 写进日志。

## 11. 实施阶段与逐阶段验收

### P0：现状审计与基线冻结

**任务：**

- 查明整合链路和检索链路的真实实现及所有 embedding 调用点。
- 记录当前 merge 语义、阈值、配置、MCP schema、提案/证据数据模型和备份格式。
- 运行基线检查，保存命令、退出码和摘要。
- 设计 A/B 接入点，列出最少需改文件；不做无关重构。

**验收：**输出一张真实文件/符号映射表；说明旧行为是否使用向量；列出回归风险、所需 migration（若有）及回滚方式。基线失败必须有日志，不允许掩盖。

### P1：统一模式配置与候选抽象

**任务：**

- 新增或扩展模式枚举和配置加载/验证。
- 把候选发现与共享决策层隔离；复用现有服务。
- 默认 B 模式；在现有可观测性中报告请求模式和实际执行模式。
- 旧 MCP 参数和响应保持兼容；仅加可选字段。

**验收：**模式配置、未知配置拒绝、默认 B、旧客户端兼容测试通过。此阶段不应改变最终自动合并语义。

### P2：完善纯本地规则模式 B

**任务：**

- 实现/完善安全规范化、稳定 fingerprint、结构化匹配及本地词法候选。
- 保留重要事实 token（否定、数字、日期、版本、单位、代码等）。
- 规则候选统一送入原有的提案与冲突治理流程。
- 确认无 embedding 依赖；加入调用计数测试。

**验收：**B 能独立完成候选扫描和整合；embedding 调用为 0；关键负例不误合并；扫描幂等且通过账户隔离测试。

### P3：实现向量辅助模式 A

**任务：**

- 复用现有真实 embedding provider，组合规则候选和语义候选。
- 增加候选数量、相似度、超时、并发与批量限制。
- 对阈值进行整合专属评测；不能用 mock 通过来代表语义验收。
- 明确 fallback 行为与真实执行模式；不能静默宣传为 A 成功。

**验收：**真实 provider 可用时能召回规则模式漏掉的标注语义改写候选；生成式 LLM 调用为 0；相似度不会直接触发自动合并；失败不会造成部分写入。

### P4：MCP、审计、健康状态与文档

**任务：**

- 更新相关 MCP 描述、可选参数（若决定支持逐请求 override）、响应状态与错误码。
- 更新 `.env.example`、README、配置说明、工具文档和运行手册。
- 区分检索 `semantic.ready` 与整合模式/能力状态。
- 记录候选策略版本、降级原因及可复现评测配置，但不记录原文或密钥。

**验收：**文档、schema、代码配置一致；旧客户端兼容；日志不泄漏记忆内容；状态能区分规则模式、真实 hybrid 和降级运行。

### P5：评测、安全回归和发布候选

**任务：**

- 添加 consolidation 专属固定评测集和两模式评估命令。
- 执行 PostgreSQL 集成测试、权限测试、并发/故障注入、备份恢复测试。
- 评估两模式的质量、延迟、模型依赖与运行成本。
- 准备回滚方案和发布说明。

**验收：**第 10 节的强制门槛全部通过；若 A 未接入真实 provider 或样本不足，必须标记为“功能可用但语义效果未验收”，不得宣称已达到生产语义整合质量。

## 12. 验收命令与运行记录

Agent 首先检查仓库现有开发指南、CI、Compose 服务名和测试约定。下列为必须尝试的基础命令；如果项目实际配置要求附加 feature、环境变量或数据库服务，应在报告中给出最终可复制命令，不得静默跳过。

### 12.1 静态检查与全量测试

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
```

如果 `--all-features` 在当前 workspace 不适用（例如存在互斥 feature），须按实际 CI 拆分运行并说明原因；不得为了通过而移除原有检查。

### 12.2 现有检索评测回归

README 当前列出的基线管道命令为：

```bash
cargo test --test eval_bench -- --nocapture
```

本任务不能修改或重置检索基线来掩盖回归。如确需更新基线，必须给出逐查询差异、数据集指纹、配置和理由，并确认属于预期行为。

### 12.3 整合专属评测

为新建的测试目标确定实际命令，例如：

```bash
# 命令名应以实际新增的 Cargo integration test target 为准
cargo test --test <实际整合评测目标> -- --nocapture
```

交付时不得保留尖括号占位符；报告必须给出实际命令、完整退出码和输出文件路径。

### 12.4 Compose / PostgreSQL 集成验收

当前 README 使用以下方式构建并启动服务：

```bash
docker compose config --quiet
docker compose up -d --build
```

## 13. 回滚与发布策略

1. **默认 B，先发布规则模式。** 在没有明确设置 A 及其 embedding 配置时，不得触发 embedding 请求。
2. 在测试和预发环境先用同一批固定数据分别运行 A/B，不要直接在生产环境同时对数据执行两套自动合并。
3. 首次启用 A 时优先使用 `dry_run`/只生成提案的方式检查候选质量；确认自动合并安全门槛后，才按现有策略允许自动合并。
4. 如果 A 出现异常，可把 `HUB_CONSOLIDATION_MODE` 切回 `rules`，或将 fallback 改为 `rules`；无需更改 OAuth、检索或数据库架构。
5. 若引入 schema 迁移，必须确保新代码在旧快照数据上工作；迁移应向后兼容。回滚应用版本前先验证旧程序可读取新 schema，若不能，则提供安全、经过演练的回滚迁移，不允许手工删列或清表。
6. 新模式不得物理删除源记忆；所有合并保留现有证据、来源与历史。若出现误合并，必须可通过当前版本历史/审计/恢复机制追溯和恢复。
7. 任何严重错误合并、跨账户访问、证据丢失或恢复失败都视为发布阻断项，不得以性能提升或召回率上升接受。
